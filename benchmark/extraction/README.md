# Real-paper extraction corpus

This directory separates **sampling-frame candidates**, **seed cases**, **reviewed gold**, **locked benchmark splits**, and any later release receipt.

A paper or case appearing here is never evidence that the paper is reliable, unreliable, reproducible, or problematic. The corpus evaluates extraction and promotion behavior only.

## Lifecycle

1. **Unlabeled sampling frame** — candidate papers live in `benchmark/corpus/candidates.json`. Presence in the frame is metadata only and carries no claim/extraction label.
2. **Pre-TEST evidence plan** — before reviewed TEST outcomes are inspected, `scripts/build_extraction_evidence_plan.py` commits exact sampling-frame bytes, normalized sampling-frame identity, exact seed-manifest bytes, deterministic seed target-universe SHA-256, independent-review protocol version, split salt, TRAIN/DEVELOPMENT split fractions, complete threshold grid, and benchmark confidence. The seed file is an explicit required input.
3. **Seed and blinded packets** — a real, legally accessible paper/display item useful for parser development. Seed cases are not benchmark gold. Exact seed bytes deterministically define the review-target universe (`case_id:key` plus paper/family/object/key/criticality and page/table/row identity). `scripts/build_extraction_review_packets.py` uses the same strict seed loader as the evidence-plan path, then emits blinded reviewer packets whose submission template matches the strict submission JSON schema. Duplicate seed keys, NaN/Infinity, unsupported schema versions, and seed identity drift fail before packets are written.
4. **Publication/input archive** — `scripts/build_extraction_input_artifact_manifest.py` hashes the exact files that will back review/prediction sources. The strict manifest records unique artifact IDs, safe relative paths, byte sizes, and SHA-256 values. Symlinks, path traversal, missing/non-regular files, duplicate IDs/paths, size drift, and byte drift fail closed.
5. **Double review and adjudication** — every numerical field, table/figure identity, row/column identity, and critical semantic gate is independently checked by at least two reviewers and then independently adjudicated before locked gold. Reviewer submissions and adjudication are strict standalone JSON archives; `scripts/build_extraction_review_record.py` binds their `target_id` back to the exact strict seed target universe, invokes `resolve_extraction_reviews()`, writes one canonical review-record archive, strict-loads it back, and prints its SHA-256. Reviewer A/B agreement is not represented as adjudication and cannot enter locked gold without a distinct adjudicator. Veritas validates the supplied identities and evidence structure but cannot manufacture genuine human independence.
6. **Family lock and derived split manifests** — all versions sharing one `article_family_id` receive one immutable train/development/test assignment under the precommitted salt/fractions. DEVELOPMENT and TEST target manifests are then deterministically derived from the exact reviewed-gold hash plus family split-lock hash; callers cannot substitute arbitrary membership digests.
7. **Development calibration** — every DEVELOPMENT threshold observation covers the complete precommitted threshold grid and carries exact `ExtractionPrediction` / `ExtractionResolution` provenance. Validation re-runs `evaluate_extraction_benchmark()` against exact DEVELOPMENT gold and precommitted confidence. The selected threshold is deterministically recomputed from the DEVELOPMENT policy and bound observations, then locked to the derived DEVELOPMENT manifest.
8. **Untouched TEST** — TEST observations use the same precommitted grid/confidence and exact prediction/resolution provenance. TEST reports are re-evaluated against exact derived TEST gold. TEST results cannot feed back into threshold selection, parser routing, input selection, execution-plan changes, or promotion-policy changes. A parser-development case does not become held out merely because it is later reviewed.
9. **Execution evidence** — canonical prediction-artifact bytes and one `ExtractionExecutionAttestation` per DEVELOPMENT/TEST threshold bind the exact execution plan, derived split manifest, threshold, prediction bytes/semantics, successful exit, disabled network, read-only source mount, and no credentials. `scripts/build_extraction_execution_plan.py` derives its manifest/source-tree/parser-registry/runtime/command commitments from concrete archived files.
10. **Release receipt** — `ExtractionEvidenceReleaseReceipt` and `AttestedExtractionEvidenceReleaseReceipt` are issued only if the reviewed-gold, split, prediction/report, calibration, TEST, curve, and execution-evidence chain validates. Both remain non-production.
11. **Canonical release bundle** — `scripts/build_extraction_release_bundle.py` consumes strict standalone review-record archives, an explicit DEVELOPMENT threshold policy, DEV/TEST threshold id/value/execution-id descriptors, canonical prediction-artifact paths, the verified publication/input manifest/root, and the release-artifact root. It requires adjudication for every included review record, verifies publication bytes and source closure, writes canonical `ExtractionReleaseEvidenceBundle` JSON, strict-loads it back, and prints its SHA-256. The builder never generates reviewer content or claims that distinct IDs prove genuine human independence.
12. **Cold release reconstruction** — `rebuild_attested_extraction_evidence_release_receipt_from_archive()` regenerates gold, split lock, split target manifests, benchmark reports, observations, execution evidence, frozen threshold, TEST seal/lock, curves, and the final attested receipt from the sampling/seed/plan/release-bundle/prediction archives. A cold verifier requires the rebuilt receipt to equal the separately archived receipt before any external signature is accepted.
13. **Source closure and signed evidence-run provenance** — `verify_extraction_release_source_artifacts()` requires every review/submission/adjudication source and every accepted prediction candidate to name an artifact ID from the already byte-verified publication manifest. The pre-TEST evidence-run trust policy then freezes the evidence plan, execution plan, source commit, trust root, and runner/repository/workflow identity; cold verification checks independently selected run id/attempt/commit and the Ed25519 signature over the **rebuilt** release/execution subject.
14. **Optional trusted source-archive build provenance** — if the evidence claim needs to say that the exact source-tree archive was produced from the named Git commit, precommit an `ExtractionSourceArchiveTrustPolicy` with `scripts/build_extraction_source_archive_trust_policy.py`, archive a signed `ExtractionSourceArchiveProvenanceStatement` from the trusted build/archive identity, and supply an independently selected build run id/attempt during cold verification. The verifier then emits a separate non-production `PrecommittedExtractionSourceArchiveReceipt` only when policy, builder root/identity, expected commit, exact execution-plan/source-tree commitment, independently selected build run context, reconstructed subject, and Ed25519 signature all agree. Supplying only part of this optional chain fails closed; supplying none leaves the ordinary evidence-run semantics unchanged.

The release workflow is deliberately stricter than a collection of hashes. It rejects mixed sampling frames, changed seed bytes, target/locator drift, missing real adjudication records, forged review hashes, post-plan split drift, caller-forged split membership, benchmark-confidence drift, missing prediction provenance, reports that do not match re-evaluation, non-canonical prediction bytes, source artifact IDs outside the verified publication manifest, execution-artifact drift, invalid TEST locks/seals, curve drift, and an archived attested receipt that cannot be reproduced from the source evidence bundle. When the optional source-archive chain is requested, it also rejects partial chain inputs, post-hoc commit/source-tree drift, wrong build-run context, wrong builder root/identity, subject drift, and invalid signatures.

## Metrics

Extraction evaluation reports separate quantities rather than collapsing them into a single score:

- selective coverage;
- accepted numerical/value accuracy;
- accepted source identity accuracy;
- table/row identity accuracy;
- critical semantic-gate accuracy;
- article-family-level wrong-accept rate and its one-sided confidence bound.

A parser that extracts the correct number from the wrong table or row is not counted as correct merely because the numeric string matches. Release validation derives per-target correctness from bound prediction/resolution objects and exact gold locations, then recomputes the aggregate report; self-authored correctness labels are insufficient.

Coverage-selectivity curves retain every precommitted threshold point and are rebuilt from exact threshold observations. Cold reconstruction additionally requires those observations to be reproducible from the canonical prediction artifacts, exact split gold, and precommitted benchmark confidence.

## Production boundary

Seed, development, TEST benchmark, release-receipt, signed provenance, successful cold-verification results, and optional source-archive receipts carry no production hard-finding authority by themselves. Production authority remains governed separately by the held-out certification path and must bind a sufficiently large corpus plus the exact parser/schema/promotion/system combination being deployed.

Mandatory cold verification proves byte/commitment/signature consistency of the supplied evidence archive. It does not prove genuine human reviewer independence, historical untouched-TEST handling, publisher/URL/license authenticity, institutional key ownership, historical pre-TEST timing, or by itself prove that a separately archived source-tree file was mechanically generated from the named Git commit.

The optional source-archive chain strengthens only that last relation: under a genuinely pretrusted builder root/policy and independently selected build context, it proves that the holder of the builder key signed the exact expected-commit → execution-plan/source-tree relation for that build run. It still does not manufacture proof that a named provider controlled the key, that the trusted workflow actually had the claimed checkout/archive semantics, or that the policy/root existed before TEST; those facts require independently governed build configuration, CI history, transparency logs, or equivalent external evidence.
